# Site Lens `v0.5.0.alpha1` 真机验证流程

日期：2026-10-25

本流程用于在 `emulator-5554` 的 alpha1 媒体专项通过后，使用真实 Android 设备完成观看保存、媒体缓存、原生播放、HLS/MP4、系统控制和 DLNA 的分层验收。

`v0.5.0.alpha1` 的 pubspec 版本为 `0.5.0-alpha1+99`，对应发布标签约定为 `v0.5.0.alpha1`。当前 alpha1 的目标是前台媒体契约和观看保存 v1.1；原生 MediaSessionService、跨 Activity/Engine 的后台恢复、共享媒体缓存和后台授权刷新仍按后续子计划验收，不能用本流程的通过结果提前宣称已支持。

## 1. 设备与环境准备

要求：

- Android 真机，建议 API 34 或更高；记录型号、Android 版本、API level、WebView provider 和 ABI。
- USB 或已经验证可用的 Wi-Fi ADB；一次验证只使用一个设备 serial。
- 设备至少保留 2 GB 可用空间；媒体专项会写入应用缓存、临时导出和测试数据库。
- 真实 DLNA 接收端与手机处于同一局域网；记录电视/盒子型号、接收端 IP、固件和支持的 MIME。
- 关闭会遮挡测试页面的系统浮窗；允许测试包通知权限和本地媒体访问所需的系统授权。

设备预检：

```sh
make devices
adb -s <DEVICE_SERIAL> get-state
adb -s <DEVICE_SERIAL> shell getprop ro.build.version.sdk
adb -s <DEVICE_SERIAL> shell getprop ro.product.model
adb -s <DEVICE_SERIAL> shell dumpsys webviewupdate
adb -s <DEVICE_SERIAL> shell df -h /data /sdcard
```

若使用无线 ADB，先完成一次连接并记录 serial；不要在测试过程中自动重连或更换设备端点：

```sh
make connect DEVICE=<DEVICE_IP>:<PORT>
make devices
```

## 2. 包、数据库和来源校验

构建测试包：

```sh
make build-debug
python3 tool/verify_release_pubspec.py --tag v0.5.0.alpha1 --version-code 99
shasum -a 256 build/app/outputs/flutter-apk/app-debug.apk
```

安装前保存设备身份和数据库备份。必须保留来源设备的序列号、Android ID 摘要、数据库清单、文件长度和 SHA-256；缺少完整来源信息的旧备份不得自动恢复到新设备。

推荐使用项目验收 runner：

```sh
python3 -u tool/run_android_acceptance.py <DEVICE_SERIAL> \
  --skip-build \
  --skip-check \
  --no-adb-recovery \
  --single-suite \
  --integration-target integration_test/media_tasks_test.dart
```

runner 会在测试前备份数据库和相关 WAL/SHM 文件，并在结束时恢复产品包和数据库。若 runner 输出 `backup retained at ...`，保留该目录，后续恢复使用：

```sh
make restore-device DEVICE=<DEVICE_SERIAL> BACKUP=<RETAINED_BACKUP_DIR>
```

不要把设备数据库、设备序列号、登录 Cookie、Authorization header、私有媒体 URL 或通知截图提交到仓库。

## 3. alpha1 自动化媒体门禁

先执行媒体专项。必须记录命令、退出码、APK SHA-256、设备信息和 runner 输出路径。

```sh
python3 -u tool/run_android_acceptance.py <DEVICE_SERIAL> \
  --skip-build \
  --skip-check \
  --no-adb-recovery \
  --single-suite \
  --integration-target integration_test/media_tasks_test.dart
```

alpha1 媒体专项必须覆盖并记录：

1. DLNA 本地中继能够绑定可达地址并返回完整文件。
2. 原生播放持有文件读租约时，删除、改名、移动和覆盖被拒绝；停止后操作恢复。
3. 缩略图文件和网络来源保持媒体原始宽高比。
4. 未完成 HLS 临时目录在取消清理后不产生 MP4 假产物。
5. 删除下载任务不会删除独立 MP4 索引和可 seek 的导出文件。
6. 本地 HLS remux 的 MP4 连续播放、暂停、seek、恢复和任务缓存清理。
7. 媒体库索引缺失后能够重新扫描恢复 MP4。
8. 任务生命周期与本地 HLS 导出门禁。
9. 观看保存从播放 owner 创建，暂停后更新位置/时长/状态，不创建媒体下载任务，并在媒体管理页面显示。

当前套件通过只证明上述自动化范围；它不证明真实站点的业务剧情标注、DRM 解密、付费墙/验证码/登录绕过、物理 BFCache 驻留或后台 MediaSession 恢复。

## 4. 观看保存人工验收

使用一个用户已授权、可稳定识别剧集和集数的站点。进入播放页后：

1. 确认当前选中标签播放第 1 集；等待页面实际播放，不使用仅出现候选但未播放的资源。
2. 打开媒体管理，确认“观看保存”出现剧名、集数、进度、状态和更新时间。
3. 暂停并等待一次状态上报；确认状态变为“已暂停”，位置向前更新，时长保持有效。
4. 恢复播放，再次暂停；确认同一集只有一条记录，旧 snapshot/eventSequence 不能把位置回退。
5. 切换到另一个标签播放第 2 集；确认新建第二个 owner，原第 1 集记录不被覆盖。
6. 关闭播放页后重新打开媒体管理；确认记录仍在，点击记录只打开原观看页面，不新建下载任务。
7. 删除观看记录；确认媒体任务、HLS 缓存、MP4 导出和媒体库索引均不被删除。
8. 使用未确认的推荐播放器、无集数资源和未播放候选；确认不会创建观看保存。

每项记录：设备 serial、页面入口、当前 tab、剧集/集数、显示进度、记录 owner 数量、媒体任务数量、截图和日志时间点。不要截图或保存敏感授权头。

## 5. 前台原生播放与系统控制回归

alpha1 只验收当前前台原生播放器：

- 从已完成本地 MP4 打开原生播放，确认播放/暂停、seek、倍速和结束状态。
- 从完整本地 HLS 导出 MP4 后播放，确认音画同步、EOS、seek 和暂停保持。
- 关闭媒体页面但保持应用前台，确认文件租约不会过早释放；显式停止后才允许删除/移动。
- 旋转屏幕、返回上级页面和重新打开媒体管理，确认没有重复播放器、残留纹理或重复通知。
- 记录当前边界：Activity/Flutter Engine 销毁后不验收后台继续播放；该能力属于后续原生 MediaSessionService 子计划。

## 6. HLS、MP4 和导出所有权

对一个完整 VOD HLS 资源执行：

1. 记录本地清单、init、音视频分片、必要本地资源的长度和 SHA-256。
2. 导出 MP4，确认导出使用本地缓存，不发生远程回源，不启用隐式转码。
3. 播放导出的 MP4 并执行 seek；同时删除下载任务，确认独立 MP4 和索引仍存在。
4. 删除导出文件后重扫媒体库，确认索引行为和恢复提示符合当前产品语义。
5. 若验证 HLS 包导出，必须逐个检查 m3u8、init、分片和本地资源路径；远程 URI、越界路径、缺失分片和未授权资源必须拒绝。

HLS 导出包与 MP4 是独立所有权。任何一个任务或观看记录的删除都不得隐式删除另一类仍被引用的输出。

## 7. DLNA 真实接收端验收

模拟器和本机 relay 单测不能替代真实电视/盒子证据。使用已完成本地 MP4：

1. 发现接收端并记录设备描述、AVTransport endpoint 和声明的 MIME。
2. 投屏后确认接收端画面、声音和标题实际出现。
3. 执行播放、暂停、seek、恢复和停止；分别记录手机 UI 状态与接收端实际状态。
4. 对 HLS 只在接收端明确支持并且资源完整时验证；否则通过本地 MP4 relay/导出路径验证。
5. 停止投屏后确认本地 relay 端口关闭、授权 token 失效、读租约释放；再执行文件删除回归。

协议 SOAP 成功、HTTP 200 或设备声明支持 MIME 都不能单独作为接收端播放通过证据。

## 8. 日志、截图和失败恢复

每批测试至少保存：

- 测试包绝对路径、SHA-256、package name、versionName、versionCode。
- 设备型号、API、WebView provider、ABI、serial 和测试开始/结束时间。
- runner 完整 stdout/stderr、Flutter integration log、`adb logcat` 媒体相关片段。
- 媒体任务状态、观看保存行、导出文件清单、HLS 资源摘要和 DLNA 接收端记录。
- 失败用例的最小复现步骤、失败时数据库备份目录和恢复结果。

恢复顺序：

1. 停止 runner，确认没有 Flutter/Gradle/adb 子进程继续写设备。
2. 使用 runner 输出的 backup 目录执行 `make restore-device`。
3. 重新安装原产品包并启动，校验数据库来源身份和 SHA-256。
4. 若恢复失败，保留原始 backup 和日志，不继续覆盖设备数据；标记该批次为失败。
5. 更换设备或重新连接前，重新执行设备身份预检，不复用上一台设备的数据库快照。

## 9. 结果判定

- `PASS`：所有适用项有当前包、当前设备和直接运行证据，且恢复完成。
- `FAIL`：任一适用项失败、runner 非零退出、数据库来源校验失败或恢复未完成。
- `BLOCKED`：外部接收端、授权站点或设备能力缺失导致无法执行；保留已完成证据，不把未执行项记为通过。

模拟器 alpha1 通过只代表自动化媒体门禁通过；真实设备、真实 DLNA 接收端、真实站点授权行为和不同 Android/WebView 矩阵必须分别记录结果。
