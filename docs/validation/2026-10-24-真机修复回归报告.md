# 2026-10-24 媒体、代理与设备回归报告

日期：2026-10-24（Asia/Shanghai）。工作树分支为 `codex/browser-startup-dock`，已发布基线为 `e175ecf` / `v0.4.0.alpha18`。本报告记录 alpha18 的本地、设备、CI 与发布证据，并记录 alpha19 候选玻璃渲染修正。

## 本轮改动

- 移除模拟器“Swap 剩余低于 1 GiB 即停止”的固定阈值，继续记录 Swap，并以高内存压力、可用内存持续过低、ADB/进程/测试进度、runner 超时和清理恢复失败作为停止条件。
- `ControlledHttp` 对已选路由后的幂等请求，在 `openUrl` 或响应等待出现 socket/超时错误时最多切换一次路由；路由解析、取消、TLS 证书错误和地址策略错误不进入该重试边界。
- `HttpProbe` 将两条路由的单次等待控制在 4 秒，总预算控制在 10 秒，避免第一条代理路由占满初筛预算。
- 播放列表按稳定来源路径、系列参数和批次身份分组，移除 WebView generation 对同一剧集播放列表的影响；同源不同系列路径、跨源媒体和混合批次保持隔离。
- 批量目录忽略“媒体 · 集数未确认”；只有唯一明确系列时使用系列目录，混合系列或没有明确标题时使用“批量媒体”。

## alpha19 候选玻璃渲染修正

- alpha15 真机记录为 `hcppEngine=true`、`quality=premium`、`fallback=false`；alpha17/18 因按 Android 36 Qualcomm/QTI 自动加入 `--enable-impeller=false`，变成 Skia/lightweight shader，这解释了高质量折射、rim 和边缘材质退化。
- 默认构建恢复 Impeller 选择，不再按设备 API 或 GPU 型号自动降级；需要诊断兼容渲染时显式使用 `-PsiteLensForceSkia=true`。
- 高质量且 Impeller 可用时恢复单一 `AdaptiveGlass` 内容边界；Skia/兼容路径只裁剪内容 sibling，避免装饰层与外层 `ClipPath` 双重抗锯齿造成边缘不一致。
- 当前本地检查：`./tool/check.sh` 通过，673 项 Flutter/Dart 测试；Android 原生单测、原生崩溃契约和显式 `siteLensForceSkia=true` 构建测试通过。

环境：`sl_g37`、Android API 37、arm64、host GPU、3072 MB、2 核、WebView `145.0.7632.218`。模拟器进程和 ADB 全程存活，宿主 `memory_pressure` 采样约 38%–48% 空闲，Swap free 约 1 GiB；未触发新的固定 Swap 停止条件。证据收集后已关闭模拟器。

模拟器完整 acceptance 未通过，失败来自设备能力边界：

- WebView 145 报告 `world=false; navigation=false`，脚本隔离、入口重定向、标签页和导入脚本等依赖 privileged WebView 能力的用例超时；
- 模拟器 codec inventory 为 64，Media3 parity 的 HEVC fixture 在模拟器上无法达到播放进度门槛；
- 模拟器仍通过了 H.264 TS/fMP4、AES-128 TS/fMP4、Media3 路径安全、HCPP/设备诊断、高质量 codec 列表、媒体库重扫、MP4 保留、后台媒体控制和 HLS 生命周期相关用例；
- 模拟器高质量 codec 观测为 `count=64 quality=premium fallback=false`，因为该用例未挂载 WebView；native WebView role 的兼容填充仍单独受平台视图策略保护。

模拟器结果保留为设备边界证据，不把模拟器失败归因于本轮网络或媒体身份修复，也不以模拟器结果覆盖真机完整验收。

## 后续真机验证用例

后续更换真机或重新安装测试包时，按以下顺序执行：

1. `make devices`，确认目标 Android serial；
2. `make acceptance DEVICE=<serial>`，确认完整 acceptance 和用户数据库恢复；
3. `python3 tool/run_android_proxy_acceptance.py <serial> --output-dir build/android-acceptance/<case>`，确认侦察、Dart/native/worker/HLS 代理阶段；
4. 在设备诊断页确认 API、WebView、HCPP、renderer policy、codec inventory；
5. 在高质量模式下分别检查普通 Flutter 页面和浏览页上方控件，记录 `quality` 与 `fallback`；
6. 检查媒体批量下载目录的真实文件系统合并、MP4 目录命名、同系列播放列表上一集/下一集和跨系列隔离；
7. 若设备断开，先保留 runner 输出和 backup 路径，再按 `make restore-device DEVICE=<serial> BACKUP=<path>` 完成恢复。
