# VPN 网络问题：现状、根因与彻底解决方案

## Read this when

需要理解「为什么同一份代码在 sing-box 下正常、在 clash.meta 下失败」，评估是否引入本地回环代理，或修改 `SystemMediaNetwork` 的路由与超时策略时。

- 记录日期：2026-11-07
- 基线：`6bcd6c2`（`refactor(network): delegate web navigation to system route`），版本 `0.6.0-alpha40+173`
- 设备：`2410DPN6CC`，Android 16（SDK 36）
- 对照客户端：`com.github.metacubex.clash.meta`（规则模式 + Fake-IP）、`moe.nb4a`（sing-box）

## 1. 现状

同一个安装包：

| 隧道 | 站点检测 | WebView | 媒体下载/播放 | 更新检查 |
|---|---|---|---|---|
| sing-box | 正常 | 正常 | 正常 | 正常 |
| clash.meta（Fake-IP + 规则） | 偶发超时 | 正常 | 失败 | 失败 |

最新一轮报错（`discovery.probe`）：

```
操作超时，请稍后重试
TimeoutException after 0:00:02.499999: Future not completed
  #1 Cancellation.waitFor (network/transport.dart:258)

系统网络请求失败
  #0 NativeSystemHttpTransport.request (network/native_system_http.dart:109)
```

`2.499999` 秒不是巧合：探针总预算 5 秒，被平分成两次尝试。

## 2. 根因分层

问题不是一个 bug，而是四层叠加。前两层已在 alpha32–alpha36 修掉，后两层是当前要解决的。

### 2.1 已解决：VPN 网络识别

规则模式 TUN 下 `activeNetwork` 仍是底层 Wi-Fi，只看它会得出「没有 VPN」。
`vpnNetwork`/`pickVpnNetwork` 改为遍历全部网络，优先 VALIDATED 的隧道。

### 2.2 已解决：Fake-IP 与真实地址的取舍

clash 对所有域名返回 `198.18.0.0/15` 合成地址，规则一旦判 DIRECT，该地址就指向空处。
`tunnelResolvesToSynthesized` 决定是否绑定隧道 socket；合成地址走隧道，真实地址走底层。

### 2.3 未解决：超时预算被切碎（当前报错直接原因）

`_fetchNative` 把调用方的 timeout **平均分配**给两次尝试：

```dart
timeout.inMicroseconds ~/ nativeTransportAttempts   // 5s → 2.5s × 2
```

而原生侧的一次尝试要依次完成：

| 阶段 | 预算 |
|---|---|
| 隧道 DNS 查询 | `min(timeoutMs, 1500ms)` |
| TCP 连接 + TLS 握手 | 剩余部分 |

在 VPN 下，DNS 冷查询经常 800–1500ms，剩下不到 1 秒做握手，正常站点也会超时。
而超时被归类为 `TimeoutException`，用户看到的是「操作超时」，掩盖了真实原因。

### 2.4 未解决：Dart 与原生两条链路并存

当前媒体走原生、WebView 走系统、脚本和更新走 `NativeSystemHttpTransport`，
三处各自决定 DNS、代理、是否绑定隧道。每个隧道客户端的 DNS 行为差异
（Fake-IP / 真实地址 / 混合）都必须在**每一处**重新处理，这是反复出问题的结构性原因。

## 3. 参考实现：easyl 的本地回环代理

easyl 不在请求层面适配隧道，而是**在进程内起一个本地 HTTP 代理**：

```
播放器 ──> http://127.0.0.1:18889/p/<id>/<encoded-url>
                │
                ├─ 本地线程池负责连接、重试、分片
                └─ 出口完全由本地进程决定
```

两个服务：

| 端口 | 用途 |
|---|---|
| `127.0.0.1:18889` | 并行流代理（`o8.p`：`ParallelProxy`） |
| `127.0.0.1:18888` | 迅雷/下载代理（`o8.d0`：`XunleiProxy`） |

核心价值：

1. **绕开系统 VPN 的 DNS 语义差异**。播放器只连 localhost，域名解析发生在本地代理内部，
   由代理自己决定用哪个解析器；
2. **绕开 WebView 与播放器的策略差异**。两者都只认 localhost，不需要各自实现 Fake-IP 逻辑；
3. **失败点收敛**。所有网络错误都发生在本地代理一处，日志和重试策略统一；
4. **不依赖隧道客户端的实现细节**。clash 与 sing-box 的差异被隔离在代理的出口选择里。

代价：

- 需要一个后台服务和一个稳定的本地端口；
- 本地代理本身就是攻击面，必须严格限制为回环 + 仅本进程可访问；
- Media3/ExoPlayer 对 localhost 的支持良好，但 HLS 的相对 URL 需要重写。

## 4. 彻底解决方案

分三步，按投入从小到大。前两步解决当前报错，第三步消除结构性重复。

### 第一步：修正超时预算（立即，本次已实现）

原则：**首次尝试给足预算，重试只看剩余预算。**

```dart
// 首次尝试：至少 4 秒，不受平分影响
// 重试：仅当剩余预算 >= 2 秒才发起
static const _nativeAttemptFloor = Duration(seconds: 4);
static const _nativeRetryFloor = Duration(seconds: 2);
```

同时保证：超时不再被笼统报告。原生侧应区分 `dns_timeout`、`connect_timeout`、
`tls_timeout`，Dart 侧据此给出可行动的文案。

### 第二步：探针预算按隧道类型伸缩（短期）

当前 `HttpProbe.candidateDeadline` 固定 5 秒，覆盖初筛和首页验证两段。
在隧道内应放宽：

```dart
// 检测到隧道时使用更宽的预算，因为 DNS 与握手都要经过隧道
Duration get deadline => tunneled
    ? const Duration(seconds: 12)
    : const Duration(seconds: 5);
```

判定依据来自 `MediaNetwork.probeRoute` 返回的 `routeKind`，不需要新增探测。

### 第三步：引入本地回环代理（结构性，建议实施）

仿照 easyl，在 App 进程内提供 `127.0.0.1:<port>` 代理，媒体与更新统一走它。

设计要点：

| 项 | 方案 |
|---|---|
| 监听地址 | `127.0.0.1`，端口随机分配后上报 Dart 层（避免固定端口冲突） |
| 访问控制 | 只接受来自本进程的连接；校验 `SO_PEERCRED`/请求头 token |
| 路由决策 | 复用现有 `SystemMediaNetwork.routePlan`，出口逻辑不再分散 |
| HLS 支持 | 重写 playlist 内的相对/绝对 URL 指向本地代理 |
| 生命周期 | 随 `MediaNetworkRuntime` 创建，进程退出即关闭 |
| 回退 | 代理启动失败时退回现有直连实现，不阻断功能 |

收益：媒体、播放、更新、甚至脚本请求全部共享同一套出口逻辑，
clash/sing-box 的差异只在本地代理内部处理一次。

风险与边界：

- 本地代理必须严格限制为回环，且要有请求 token，否则会变成同机其他应用的开放代理；
- 需要处理代理与系统 VPN 同时存在时的环路（代理自身出站不能再经自己）；
- HLS/DASH 的密钥请求、init 段、分片都需要同样的 URL 重写。

## 5. 本次已实施的改动

只做第一步，因为它直接对应你贴出的 `2.499999` 秒超时：

- `_nativeAttemptFloor`（4 秒）与 `_nativeRetryFloor`（2 秒）；
- 首次尝试取 `max(平分值, 4 秒)` 但不超过调用方总预算；
- 重试仅在剩余预算足够时发起，否则立即抛出最近一次真实错误。

未实施第二、三步：第二步需要隧道状态贯通到探针，第三步是一次结构性重构，
两者都应在拿到本次改动的设备结果后再动。

| 结论 | 依据 |
|---|---|
| 规则模式 TUN 不一定接管 `activeNetwork` | 设备 `dumpsys connectivity`：`Active default network` 指向 WIFI |

## 8. 第二条根因：TLS 握手被重复执行

`alpha42` 的 sing-box 日志证明**绑定本身是成功的**：

```
inbound/tun[tun-in]: inbound connection from 172.19.0.1:48792
router: found package name: dev.vikiea.site_lens
outbound/vless[proxy]: outbound connection to 99.86.18.85:443
```

请求经 tun 进入、被识别出包名、从节点出站——但应用侧仍然超时。瓶颈在隧道之外。

`bindToNetwork` 同时替换了 OkHttp 的两个槽位，而 `TunnelSslSocketFactory`
把 `createSocket(host, port)` 系列实现成「返回 tunnel 的裸 socket」，并在
`createSocket(Socket, host, port, autoClose)` 里手动调用 `startHandshake()`。

OkHttp 的真实调用顺序是：

```
raw = socketFactory.createSocket()          // 已绑定但未连接
raw.connect(address)                        // 经隧道建立 TCP
ssl = sslSocketFactory.createSocket(raw, host, port, true)
```

第三步 OkHttp 自己会握手。而我们的实现又调用了一次 `startHandshake()`，
同一字节流上出现两次握手，TLS 状态机错位，连接一直挂到超时——正是
「TCP 已到 `99.86.18.85:443`，却没有任何 HTTP 响应」的表现。

修复：`TunnelSslSocketFactory` 只做委托。

- 无参及各 `createSocket(...)` 重载全部转给平台默认 `SSLSocketFactory`；
- `createSocket(Socket, ...)` 同样委托，由 OkHttp 决定何时握手；
- 不再手动 `startHandshake()`。

绑定仍然生效：socket 对象由 `Network.getSocketFactory()` 创建，连接与握手都在
这个已绑定的 socket 上进行；证书校验保持平台默认。

## 9. 第三条：诊断信息被吞掉，导致无法定位

alpha43 的 sing-box 日志证明网络路径是通的：

```
inbound/tun[tun-in]: inbound connection from 172.19.0.1:33798
router: found package name: dev.vikiea.site_lens
outbound/vless[proxy]: outbound connection to 13.35.163.40:443   (332ms)
```

隧道识别、绑定、出站全部正常。但应用仍报超时，且**报错恒为同一句**：

```
系统网络请求超时
  #0 ControlledHttp._fetchNative (transport.dart:1008)
```

逐行走查 `_fetchNative` 的预算分配后确认：探针给 5 秒，首次尝试取
`min(5s, max(2.5s, 4s)) = 4s`，第二次进来时剩余不足 2 秒，直接走到第 1008 行
抛出通用文案。而第 1008 行能被执行，意味着 `lastError` 为 null —— 首次尝试是
被 Dart 侧的 `.timeout()` 掐断的，`on TimeoutException` 分支只推进了路由索引，
**没有保存任何错误**。

后果：DNS 卡住、TCP 被拒、TLS 不匹配、服务端不回首字节，四种完全不同的问题
在应用侧看到的都是「系统网络请求超时」。

### 本次改动

**Dart 侧**：`on TimeoutException` 记录 `NativeSystemHttpException('timeout', ...)`
并带上实际预算毫秒数，使下一次尝试或最终报错能保留真实来源。

**原生侧**：新增 `PhaseProbe`（OkHttp `EventListener`），记录每个阶段的时刻：

```
dnsStart / dnsEnd / connectStart / connectEnd / connectFailed
tlsStart / tlsEnd / requestStart / requestSent / responseHeaders
failed / end
```

失败时输出一行：

```
SiteLensNetDiag: failed route=... dns=... bind=... timeoutMs=...
  uri=<host> attempt=<n> reached=<最后到达的阶段> dnsEnd=12ms connectEnd=88ms ...
  error=<异常类型>: <消息>
```

`reached=` 直接指出卡在哪一步：

| reached 值 | 含义 | 修复方向 |
|---|---|---|
| `none` / `dnsStart` | DNS 未返回 | 隧道 DNS 或 resolver 线程池 |
| `connectStart` | TCP 未建立 | 隧道不转发该地址 |
| `connectEnd` | TCP 通、TLS 未开始 | OkHttp 连接复用或 socket 绑定 |
| `tlsStart` | TLS 握手未完成 | 证书、SNI 或隧道截断 |
| `requestSent` | 请求已发出、无响应头 | 服务端或隧道出站 |

`EventListener` 的重写方法已对着真实 `okhttp-4.12.0.jar` 用 `javac` 编译验证，
不是凭记忆写的签名。

### 下一步

拿到 `SiteLensNetDiag` 那一行即可定位；在此之前不再改绑定或 TLS 逻辑。

## 10. 真正的根因：绑定 socket 在规则模式 TUN 下不可达

前几节的方向错了。决定性反证来自一个矛盾：

> 探针报超时，但点进站点后 WebView 正常访问、媒体正常播放。

如果隧道不通，WebView 也应该失败。既然 WebView 正常，说明隧道本身是好的，
差别只在**socket 的创建方式**。

### 10.1 两条路径的差异

| | WebView | 探针（alpha42 之后） |
|---|---|---|
| socket 创建者 | Chromium 自己的网络栈 | OkHttp + `Network.getSocketFactory()` |
| 是否绑定 Network | **否** | **是**（绑定到非默认的 VPN） |
| 源地址 | 系统默认网络 | `172.19.0.1` |
| 结果 | 正常 | 4 秒超时 |

### 10.2 设备实测

```
/proc/net/route:
  tun0   172.19.0.0/30     ← 只有本地网段
  rmnet_data1  10.3.147.192/21

dumpsys connectivity (VPN 的声明):
  Routes: [ 1.0.0.0/8, 2.0.0.0/7, ... ]   ← 声明了全局
```

**声明与内核不一致**。规则模式的 TUN 向 `ConnectivityManager` 声称拥有
`0.0.0.0/0`，但内核路由表里 `tun0` 只有 `/30`。真正的分流发生在
fwmark/iptables 规则里，按 **uid** 匹配，把流量重定向进 tun。

### 10.3 绑定的后果

`Network.bindSocket` 会让 socket 只能从该网络出。于是：

1. socket 绕过按 uid 的 fwmark 规则（已显式指定网络，规则不再适用）；
2. 内核路由表里 `tun0` 又没有默认路由；
3. 目的地址**没有任何可用路由** → 连接被挂起；
4. 4 秒后 Dart 侧超时，报「系统网络请求超时」。

不绑定时，socket 走 `rmnet_data1` 的默认路由 → fwmark 规则捕获 →
重定向进 tun → sing-box 按包名识别 → 从节点出站。这正是 WebView 走的路。

### 10.4 结论

**非默认路由的隧道禁止绑定 socket。** 唯一需要绑定的是合成地址
（Fake-IP），因为它只有隧道能翻译。

`shouldBindVpnSocket` 现在只保留一个条件：

```kotlin
fun shouldBindVpnSocket(info: RouteInfo, proxy: Proxy): Boolean {
    if (proxy.type() != Proxy.Type.DIRECT) return false
    return info.kind == RouteKind.VPN_TUN_FAKE_IP && info.dnsClass == "fake_ip"
}
```

`vpnIsDefault` 不再参与决策，只作为诊断字段输出。

### 10.5 此前的判断为何错了

alpha42 观察到「隧道非默认 → 不绑定就走底层」，于是加上绑定条件。
当时的推断缺少一步：不绑定的 socket 确实先走底层默认路由，但**隧道会用
fwmark 规则把它抓回来**。只看到「源地址是底层」，没验证「流量最终去了哪里」。

丢掉的验证很直接：如果绑定是必需的，WebView 就该失败——它从不绑定。

## 11. 规则模式的两类真实形态（alpha47）

### 11.1 混合 DNS 答案是常态，不是异常

规则模式按规则分别处理每个域名，因此同一个名字可能返回：

| 答案 | 含义 | 正确处置 |
|---|---|---|
| 全部 `198.18.x.x` | 隧道合成，只有隧道能翻译 | 绑定隧道 socket |
| 全部真实公网 IP | 规则判 DIRECT | 直连 |
| **混合** | 一个答案里两种都有，或两次查询结果不同 | **保留真实 IP，忽略合成地址** |

旧实现用 `addresses.all(::fakeIp)` 判 `onlyFakeIp`，只要混入一个真实 IP 就掉进
`PUBLIC_DIRECT` 分支 —— 而该分支的 `require(addresses.all(::publicAddress))` 又会
因为 `198.18/15` 被判为非公网而抛异常。结果：混合答案直接失败。

现在 `planFor` 先挑出真实公网地址，非空就用它们走 `PUBLIC_DIRECT`
（`dnsClass` 记为 `mixed` 便于诊断），只有全是合成地址时才依赖隧道。

### 11.2 能力标志可能被隐藏

sing-box 场景实测：

```
route=public_direct  dns=public  bind=false  vpnDefault=true
dnsEnd(13.35.163.40,...)=1ms
```

`vpnDefault=true` 且 `route=public_direct` 说明 `vpn=false`，即
`capabilities.hasTransport(TRANSPORT_VPN)` 返回了 false。但同一时刻：

```
隧道 DNS 172.19.0.2 -> 13.35.163.40 ✅
路由器 DNS 192.168.2.1 -> 超时 ❌
```

应用拿到的地址只能来自隧道 DNS，证明 `routeNetwork()` 返回的确实是隧道网络。
**网络可用，能力标志不可见。**

`vpnNetwork` 与 `routePlan` 现在都接受第二种证明：`looksLikeTunnelInterface`，
即接口名属于 tun/ppp/utun/wg/tap，且链路是点对点 `/30` 或声明了默认路由。
Wi-Fi 与蜂窝链路不满足该形态，因此不会误判。

### 11.3 三种部署的判定结果

| 部署 | 接口 | 能力标志 | 判定 | 结果 |
|---|---|---|---|---|
| sing-box VPN | `tun0` + `/30` | 被隐藏 | 接口形态命中 | 走隧道分支 |
| clash.meta VPN | `tun0` + `/30` | 可见 | 两者皆符 | 走隧道分支 |
| openclash 软路由 | 无 | 无 | 都不命中 | 正确判为无隧道 |

### 11.4 关于 `172.19.0.2`

不是 Fake-IP。`172.19.0.1/30` 是 tun 的本机地址，`172.19.0.2` 是同一 `/30`
点对点链路的对端 DNS。Fake-IP 使用 `198.18.0.0/15`。`192.168.x.x` 是局域网，
与 tun 的 CGNAT 段互不冲突。
