# 网络链路分治方案：回到已知良好状态

## Read this when

需要修复「站点探测超时 / GitHub 元数据失败 / 媒体嗅探异常」，或需要理解 alpha15 与当前版本在传输层选择上的差异时。

- 记录日期：2026-11-08
- 已知良好版本：`v0.6.0.alpha15`（探测 <300ms，sing-box 下 GitHub 可访问）
- 回归起点：`v0.6.0.alpha40`（提交 `214ac04`，引入统一原生通道）
- 当前：`v0.6.0.alpha47+180`

## 1. 三个独立问题

之前把它们当成一个问题修，这是反复推翻的根源。

| # | 现象 | 真实原因 | 引入版本 |
|---|---|---|---|
| A | 站点探测 4000ms 无响应 | 探测走原生 `NativeSystemHttpClient` | alpha40 |
| B | GitHub 元数据失败 | 更新走原生 + `requestTimeout: 4s` | alpha40 |
| C | 媒体嗅探取不到全集 | 站点 URI 格式变化，与网络无关 | — |

C 独立处理，本方案不涉及。

## 2. 证据

### 2.1 alpha15 与当前的实际差异

| 链路 | alpha15 | 当前 |
|---|---|---|
| 探测 | `HttpProbe(resolve: secureDns, routeForAttempt: probeRoute)` | 同上 **+ `nativeTransport`** |
| 更新 | `UpdateService(resolve: app.secureDnsResolver.resolve)` | `GitHubReleaseClient(client: NativeSystemHttpClient(requestTimeout: 4s))` |
| 媒体下载 | `ControlledHttp(resolve: secureDns, mediaRoute...)` | 同上 **+ `nativeTransport`** |

`probeRoute` 在 alpha15 已存在，形状相同 —— 它不是变量。**变量只有 `nativeTransport` 与更新链路的客户端选择。**

### 2.2 设备实测（clash.meta，Fake-IP）

```
隧道 DNS api.github.com          -> 198.18.0.9   (Fake-IP)
TCP 连 198.18.0.9:443            -> OK
TLS SNI=api.github.com           -> OK (TLS_AES_128_GCM_SHA256)
HTTP GET /repos/.../releases/latest -> 403 rate limit exceeded（请求已到达 GitHub）
```

结论：**网络路径完全正常**。clash 下 GitHub 失败的原因在应用侧的传输选择与超时预算，不在隧道。

### 2.3 为什么原生通道更脆弱

Dart `HttpClient` 零干预：不指定 Network、不自定义 DNS、不改 socket 工厂，全部交给系统路由与隧道的 fwmark 规则。任何隧道实现都能工作。

原生通道需要在四个点上判断正确：VPN 形态、DNS 归属、Fake-IP 语义、绑定时机。任一判断错误就全线失败，且失败表现为统一的「超时」，无法定位。

## 3. 改动点

### 改动 1：探测移除 nativeTransport

**文件**：`lib/ui/app_controller.dart`

**当前**（约 352–366 行）：

```dart
HttpProbe(
  resolve: secureDnsResolver.resolve,
  nativeTransport: nativeSystemTransport,      // ← 删除此行
  routeForAttempt: Platform.isAndroid
      ? (uri, attempt) =>
            MediaNetwork().probeRoute(uri, attempt: attempt)
      : null,
  onFailure: (error, stack, context) => AppErrorLogger.capture(...),
)
```

**目标**：删除 `nativeTransport` 一行，其余保留。

**依据**：alpha15 无此行，实测 <300ms。

**影响**：`HttpProbe` 回到 Dart `HttpClient` 路径，由 `_HttpHopClients` 管理连接。

---

### 改动 2：更新链路恢复 Secure DNS

**文件**：`lib/update/update_controller.dart`

**当前**（约 27–38 行）：

```dart
client: Platform.isAndroid
    ? GitHubReleaseClient(
        client: NativeSystemHttpClient(
          requestTimeout: const Duration(seconds: 4),
        ),
      )
    : null,
tokenLoader: tokenStore.read,
resolve: Platform.isAndroid ? null : app.secureDnsResolver.resolve,
routeResolver: Platform.isAndroid ? null : mediaNetwork.route,
nativeBackend: Platform.isAndroid ? MethodChannelUpdateBackend() : null,
```

**目标**：

```dart
tokenLoader: tokenStore.read,
resolve: app.secureDnsResolver.resolve,
routeResolver: null,
nativeBackend: Platform.isAndroid ? MethodChannelUpdateBackend() : null,
```

即：移除 `client:` 参数，`resolve` 在 Android 上也启用 Secure DNS，`routeResolver` 保持 null。

**依据**：alpha15 正是此形态，且 Secure DNS（DoH）返回真实 IP，天然规避 Fake-IP 语义问题。

**为什么 `routeResolver` 保持 null**：`_prepareRoute` 在 resolver 抛异常时会调用
`_connectionPolicy.block(uri)`，把该主机指向 `PROXY 127.0.0.1:9`（死端口）。
`MediaNetwork().route` 依赖原生通道，可能抛异常，一旦触发会让 GitHub 元数据
从「慢」变成「必定失败」。alpha15 的 `routeResolver` 也是 null。

**保留** `nativeBackend`：它只负责 APK 下载，与元数据请求无关。

**影响**：`_createUpdateClient` 走 `resolve != null` 分支，使用 `NetworkPolicy.connect` + `findProxy`。

---

### 改动 3：媒体下载保留原生，但移除重复干预

**文件**：`lib/ui/app_controller.dart`（约 234–243 行）

**当前**：

```dart
http: ControlledHttp(
  resolve: secureDnsResolver.resolve,
  nativeTransport: nativeSystemTransport,      // ← 删除
  mediaRouteForAttemptWithDocument: ...,
  mediaRouteForAttempt: ...,
),
```

**目标**：删除 `nativeTransport`。

**依据**：媒体下载的实际传输由 `policyTransfer: MediaNetwork().transferFileWithPolicy` 承担（原生 Kotlin），`ControlledHttp` 只处理授权与元数据。两套原生路径并存造成重复判断。

**注意**：媒体**播放**（Media3）仍走 `NativeMediaRuntime`，不受此改动影响。

---

### 改动 4：脚本与 WebView 宿主

**文件**：`lib/ui/app_controller.dart`（约 173、181 行）

**当前**：`ScriptService` 与 `NativeHosts` 的 `ControlledHttp` 都带 `nativeTransport`。

**目标**：**保持不变，本方案不动**。

**理由**：这两条链路你未报告故障，且 WebView 导航依赖系统路由，改动风险高于收益。待改动 1–3 验证后再评估。

## 4. 保留不动的部分

## 6. 回退策略

改动集中在两个文件的四处 wiring，回退成本低。

如果 Dart `HttpClient` 路径在 openclash 下 DNS 超时（`192.168.2.1` 对国外域名无应答），
则 Secure DNS（DoH）是兜底 —— 这正是改动 2 启用的能力，`HttpProbe` 的
`resolve: secureDnsResolver.resolve` 已具备同样条件。

若 Secure DNS 也未启用（用户设置为 off），需单独决定是否强制启用。
