# 远程播放的缓存层与下载分账

**Status**: accepted

## Context

T7（#19）要求「看过的内容不再重复下载」：远程播放经过一层缓存数据源，重复访问
同一分片命中缓存；同一集在后台下载时播放不受影响，也不切到本地文件。ADR-0005
已经确定下载是独立动作、播放途中不切换 `MediaItem`，因此缓存只能长在数据来源
上，不能长在下载器上。

Media3 已经随项目自带 `media3-datasource`（`SimpleCache` / `CacheDataSource`），
没有引入新依赖的理由。

真正的风险不是「怎么缓存」，是**同一份字节被两处存储同时记账**：一旦缓存与下载
共用目录，清缓存会删掉下载，或者下载进度被缓存回收清掉；一旦两者用同一套键，
播放与下载会抢同一份文件的写句柄。

## Decision

- **缓存与下载分两个目录**。缓存在应用私有 `cacheDir/media_playback_cache`
  （系统可回收），下载在 `Download/site-lens`。两者由
  `NativeMediaPlaybackCachePolicy.overlapsDownloadRoot` 做最后一道校验：目录一旦
  相交，这次播放直接不经过缓存，而不是共用文件。
- **缓存键带站点身份**。键是 `profile=<id>|host=<host>|<远端路径>`，再取 SHA-256
  作为 media3 的键。query 不参与：站点给同一分片挂不同短期令牌，按 query 分键会
  把缓存拆碎；真正区分资源的档案与 host 已经在前缀里。两个档案的同名路径因此
  不可能互相命中。
- **同一份字节只归一边**。下载队列以 Dart 的 `cacheKey` 为主键，播放这边的键是按
  站点身份算的摘要，两者天然对不上；能对上的是远端路径。所以准入判定用路径：
  下载任务里任一地址的路径与这次请求的路径互相包含（`/a/b` 与 `/a/b/seg.ts`
  两个方向），这次播放就不进缓存，只读远端。宁可少缓存一次，也不让同一份字节
  落在两份存储里。
- **容量与回收是显式的**。上限 512 MB，回收目标 384 MB。`SimpleCache` 用
  `NoOpCacheEvictor`，不在读路径上偷偷删文件；每次播放在释放缓存实例之后按
  「最近使用」从旧到新删，直到总量落进目标值。最近使用的那个足迹不论多大都留
  下，正在播的那一份不会回收自己。
- **清除缓存是独立动作**。它只删缓存目录里 media3 写下的条目，从不碰下载目录；
  已经完成的下载任务因此不受影响。清除会先让播放这一侧释放缓存句柄，正在播的
  分片仍在内存与远端，播放本身不受打断。
- **播放中下载不切本地文件**。下载只更新任务状态；当前会话的 `MediaItem` 不变，
  解码器不重建（ADR-0005 已否决热切换）。

## Rejected options

- **让下载写进 `SimpleCache`**：下载的产出是可移动、可导出的媒体文件，要能被
  文件租约与媒体库接管；缓存是可丢弃的。两者生命周期不同，放一处必然要写一套
  让两边都退让的规则。
- **按 `cacheKey` 作为唯一归属依据**：Dart 与 Kotlin 两套键算法必须逐字一致才能
  判定，任何一侧改格式都会静默退化成「两边都写」。按远端路径判定更笨，但失败时
  只会退化成「这次不缓存」。
- **读路径上做 LRU 淘汰（`LeastRecentlyUsedCacheEvictor`）**：它会在读取途中删
  文件，和正在播的分片抢；显式回收只在播放结束后发生，语义清楚。

## Consequences

- 远程播放这次会话的缓存由 `NativeMediaPlaybackCache` 独占；会话释放后缓存关闭，
  下次播放重新打开。跨会话的缓存仍然保留在磁盘上，命中照样不发网络请求。
- 缓存的占用与会话步调一致：一次播放结束就压回上限；进程被杀时留下的超额部分
  在下一次播放结束时回收。
- 清缓存与下载不会互相看见：`site_lens/native_download` 的
  `playbackCacheStatus` / `clearPlaybackCache` 只碰缓存目录。
