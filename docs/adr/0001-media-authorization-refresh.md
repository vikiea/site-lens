# 授权刷新以重新加载来源页并采用页面自身的主清单请求为准

**Status**: accepted

## Context

媒体任务的下载地址会随站点会话失效：签名过期、页面重新初始化、或用户早已离开播放页。此时任务进入“需要重新授权”状态，用户从任务行触发重试，期望重新得到可用的媒体地址。

可选的实现方式不止一种。站点把授权状态主要放在会话凭证里，但真正决定“这个页面此刻在用哪个主清单”的信息只存在于页面自身的播放初始化过程中：页面可能根据登录态、剧集、清晰度或播放器配置选择不同的清单，这个选择无法从凭证状态推导出来。

## Decision

授权刷新重新加载任务的来源页（不显示给用户），让页面自己重新走一遍播放初始化，并采用页面在这次加载中自己发起的主清单请求作为新的媒体地址，用它替换任务上的媒体地址。

页面发出请求这件事本身就是授权的证据：地址由站点的播放器用当前会话产生，因此与页面此刻真正在播放的内容一致。刷新只负责取得这个地址，是否接受由应用层按既有的地址校验与资源身份规则决定。

### Rejected options

- **只重新校验凭证（cookie-only revalidation）**：读一次凭证、比较它是否变化，据此判定刷新成功。被否决是因为凭证没变不等于地址可用——签名过期、清单地址被站点轮换、页面根本没重新初始化时，凭证都可能毫无变化；而凭证变了也无法说明页面此刻选用的是哪个清单。这个做法只能给出“授权可能仍然有效”的猜测，却会被当作“已刷新”报告，正是用户反复看到同一句“需要重新授权”的成因之一。
- **让用户手动回到播放页导航**：提示用户自己去找到站点、打开那一集、再重新选择媒体。被否决是因为任务已经记录了来源页，把这一步交还给用户是把可以自动完成的工作变成了记忆负担；而且用户是否“确实授权成功”无法被观察，只能再次靠猜测判定，问题原样复现。

### Consequences

- 刷新结果不能是“成功/失败”两态，必须是三态：**刷新成功**（取得了可采用的地址）、**授权未变化**（页面重新加载后授权状态没变、也没有可取用的地址）、**需回播放页**（未能取得可用地址，需用户回到来源页重新选择媒体）。捕获失败必须如实报成后两者之一，而不是报成功；一个“悄悄什么都没做”的刷新在用户眼里与坏了没有区别。
- 刷新需要一次真实的页面加载，因此批量刷新同一来源页的多个任务时，需要让它们共用一次加载，并让每个任务只领取属于自己的那份地址，否则一个页面的捕获会被错配到别的任务上。
- 刷新路径承载的是页面自己产生的地址，因此该路径上的任何附加脚本注入、凭证外泄或地址写入诊断日志都会破坏这个决定的前提：地址是借来的、不是应用自己造的。
- 站点改版或页面不再为某个任务发出主清单请求时，结果只能落到“需回播放页”，跨域恢复授权不在这个模型的覆盖范围内。
