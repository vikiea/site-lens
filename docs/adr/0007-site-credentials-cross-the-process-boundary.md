# 站点凭证由应用持有，并跨进程边界注入到播放与下载

**Status**: accepted

## Context

直连站点的登录状态不是一个 cookie 能表达的：访问令牌在请求头里，cookie 仍然决定 CDN 分片能不能取，设备标识参与服务端判定。

现有应用把登录状态完全交给 WebView 的 cookie 存储，下载时按重定向目标逐跳重算 cookie，凭证从不经过应用自己的层。这套安排在浏览出口上是正确的——凭证属于页面，不属于应用。直连出口上它直接失效：播放器取分片时不带页面给的凭证就会拿到 403，而任务会把这记成「媒体地址不可用」，把用户引向错误的重试。

更麻烦的是进程边界：应用侧的敏感存储是 `flutter_secure_storage`，而原生播放与下载侧的存储全是各自的 `SharedPreferences`，原生没有任何读取应用侧安全存储的入口。

## Decision

应用为每个站点档案持有一份**站点凭证**（访问令牌、刷新令牌、cookie、设备标识），由应用保存，并**跨进程边界推送给原生**：

- **推送方向单向**：凭证由应用侧写入，原生侧只读；凭证值不作为任何通道的返回值回到应用侧。
- **原生侧消费**：播放侧的数据源按当前基站取凭证注入请求头与 cookie；下载侧沿用既有的逐跳重算，但请求头来自同一份凭证。WebView 的 `AndroidCookieReader` 只服务浏览出口与镜像线路。
- **凭证失效由原生发现、由应用处置**：原生在 401/403 时回传「凭证失效」事件，应用侧发起一次凭证刷新，成功后重新推送凭证，原生重试一次。这条链有界且可配；刷新失败落到可行动的用户提示（重新登录），不静默重试。
- **凭证租约**：远程播放会话在其生命周期内持有凭证租约，期间凭证不被覆盖或吊销（见 ADR-0005）。
- 凭证的持久化位置必须与导出、备份路径显式隔离。既有 `pack_approvals` 表注释「永不导出」是同一类要求。

浏览出口的登录状态仍只归 WebView，不进入这个模型。

## Rejected options

- **每次播放在方法调用参数里下传凭证**：token 会出现在桥接参数与可能的错误日志里，且原生侧的下载工作线程拿不到。
- **让 WebView 的 cookie 存储当唯一真相**：令牌在请求头里，cookie 存储读不到；凭证过期后应用连「该刷新了」都无法判断，只能靠播放失败反推。
- **原生侧自行解密应用侧的安全存储**：等于复刻插件的存储算法，脆弱且与插件版本强耦合。
- **每个适配器自己管凭证**：刷新、失效、登出、多账号会在每个站点重写一遍，且播放侧永远不知道凭证存在。

## Consequences

- 凭证存在**生产端与消费端两份副本**，必须定义失效协议：谁在什么条件下覆盖谁、原生读到旧凭证时如何自愈。这条协议比凭证本身更容易出错。
  （T4 落地：生产端每次推送整份覆盖消费端，被拒绝的推送不覆盖；消费端只读、从不回写；
  原生读到过期或不认识的副本时当作没有凭证，不自行刷新，只把 401/403 交回应用；
  应用续期一次并重推，原生重试一次，续期失败落到「需要重新登录」。见 ADR-0009。）
- 凭证模型为主键预留账号维度（首期只有一个默认账号），避免以后补多账号时同时改动凭证表、注入路径与 UI 三处。
- 「任务需要重新授权」这个既有状态对直连出口改由凭证刷新承担，两种结局不能合并成同一条文案。
- 设备标识有生成规则要落地；它属于站点专有逻辑，止步于适配器（ADR-0004），但它的存储属于凭证。
