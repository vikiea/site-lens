# 直连出口的播放语义：远程直连为默认，下载是独立动作

**Status**: accepted（远程直连是终态默认；凭证落地前的过渡约束见 ADR-0008，开关在凭证检查到位后应被取代）

## Context

现有播放入口围绕「先下载、再播本地文件」设计：建任务、等本地文件就绪（上限 30 秒）、再交给原生会话。原生会话（`NativeMediaSessionService`）只接受 `file` 与 `content` 两种 scheme，HLS 固定使用只读已提交分片的 `GrowingFileDataSource`。

另有一条进程内的远程播放分支（`NativeMediaRuntime` 内部自建 ExoPlayer），它没有媒体会话、没有通知栏、没有后台策略、没有文件租约。它今天能跑，但不在服务里。

直连出口的体验指标是「点开就播」。把远程播放接到那条进程内分支上，等于让直连站点的用户在锁屏、通知栏、后台播放上永远缺一块。

## Decision

直连出口的播放走**服务内的远程直连**：媒体地址回到 `NativeMediaSessionService`，由服务自己构造数据源并立即开播；缓存随之发生，播放不再以「下载完成」为前提。

- 服务接受 `http`/`https`。数据源的选择按 scheme 与「是否已有可播放本地文件」分流：本地文件继续走既有的 `GrowingFileDataSource`，远程走带站点凭证的数据源（凭证注入见 ADR-0007）。
- 进程内的远程播放分支不做主路径，收束进服务；保留它作为服务不可用时的降级是**不**采用的，因为它带来第二套会话状态机。
- 下载是用户显式发起的独立动作。用户在同一集播放途中点下载时，**当前播放不切换**到本地文件：本地文件完成后只更新任务状态，下次点开才走本地。边下边播在直连出口上的语义因此收窄为「下载中的任务可以播放已缓存的分片」，这正是既有 `GrowingFileDataSource` 已经提供的能力。
- 远程会话**不持有文件租约**，改为持有凭证租约：会话期间站点凭证不被覆盖或吊销。同一候选可以同时存在远程播放与本地下载，两者不互相排他。
- 远程播放可以不建任务。没有任务时不使用 `MediaTaskState` 表达播放结局，而是使用远程特有的失败归因：
  - **凭证失效** → 触发一次凭证刷新并自动重开；刷新失败才提示重新登录。
  - **清单失效** → 重取清单后再开一次。
  - **分片失败** → 报给用户并提示可下载该集。
- 失败归因的重试有界且可配；禁止静默重试。

浏览出口的「先下载再播」语义不变。

## Rejected options

- **保留两套播放器，把进程内远程分支升级为快路径**：锁屏、通知栏、媒体键、后台策略四件事会永久缺失，而播放类应用的用户第一个会试的就是锁屏。
- **新增第三套专给直连出口的播放器**：三份媒体会话状态机无法维护。
- **远程会话占用候选、禁止同候选下载**：让「边下边播」这个名字自我否认，而且用户没有理由不能一边看一边存。
- **下载完成时热切换本地文件**：Media3 切换 `MediaItem` 会重建解码器，出现可见卡顿与音频断点；收益只是省一点缓存，不值得。

## Consequences

- `NativeMediaSessionService.open()` 的 scheme 白名单要放开到 `http(s)`，并且必须能区分「远程会话」与「本地会话」——两者在租约、可恢复状态（`restorable`）、冷恢复三处的语义不同。这是首期风险最高的一处改动，落在项目里最敏感的文件上。
- 远程会话的失败不能全部塞进既有任务状态机。以「有任务才算有结局」的旧假设写新代码，会逼出没有任务却要写任务状态的畸形分支。
- 远程播放的进度持久化需要独立于 `native_playback_positions`（该表主键是 `task_id`）。追剧位置见术语表「追剧记录」。
- 边下边播的验收口径变了：原先验证的是「任务下载中能播已提交分片」，现在还要验证「远程播放中同一集下载不打断播放」。
