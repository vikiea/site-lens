# 站点适配器的边界：站点差异止步于适配器

**Status**: accepted

## Context

站点档案（`SiteProfile`）已经是这个产品的第一等对象：它聚合发布页、候选落地页、绑定脚本与健康状态，「镜像发现」是既有能力而不是新需求。要接入只提供接口的站点（客户端协议自己加密、鉴权在请求头、内容以目录形式直取），最省成本的形状不是新增一个平行对象，而是让这份档案多一条出口。

直连站点的差异很杂：传输包络、响应加密、请求签名、设备标识、域名兜底、凭证刷新方式。这些一旦漏进上游或下游，就会在两个地方同时出现同一套逻辑。

## Decision

站点档案增加出口维度，出口只有两种：直连出口与浏览出口，同一份档案可以同时具备两者。发布页、候选落地页、健康徽章、粘 URL 侦察这些既有能力对两种出口原样复用。

直连出口由一个**站点适配器**实现，适配器绑定在档案上。适配器的职责边界：

- **内部允许**：传输包络、加密、签名、设备标识、域名发现与兜底、凭证刷新协议、目录解析。这些是站点专有逻辑，止步于此。
- **对外暴露**：目录（剧场 feed、剧集、选集）、线路及其媒体候选、站点凭证、登录页地址与登录成功判定、当前可用基站、健康自检。
- **明确不暴露**：加密方案的类型、签名算法的参数、某个站点的域名池形状、底层 HTTP 客户端、重试策略。适配器的方法签名里不应出现任何站点专有名词。

适配器注册表存在，即使首期只有一个实现：粘一个地址进来，应用要能判断「这是哪个站点、该用哪个适配器」，识别不了就明说暂无适配器。这是「多站点套壳」的最低可验证形态。

站点档案的出口字段先落库（第一次迁移只加这一项），凭证与目录缓存表随后单独迁移。

## Rejected options

- **新增平行概念 `DirectSite` 与档案并列**：会让发布页发现、存活检查、侦察三件事各写两遍，而它们与出口无关。唯一的反向论据是「平行新表零迁移成本」，但一次加列迁移的代价远低于长期维护两套发现体系。
- **把直连站点伪装成浏览站点**：直连出口没有页面可重放，授权刷新会永远落到「需回来源页」，等于把一个必然失败的机制留在热路径上。
- **首期只写死一个适配器、不做注册表**：退化成专用 app，接第二个站点时要返工侦察与档案创建两处。
- **首期就把第二个站点的骨架建起来**：没有真实需求驱动的抽象，形状会错。

## Consequences

- 术语必须分两套：出口层级用「直连出口 / 浏览出口」，剧集层级用「线路」。把「线路」当出口的同义词会让 UI 文案与内部模型对不上——用户选的是一条线路，适配器产出的是候选。
- 适配器是站点专有逻辑的**唯一**合法住处。任何在适配器外出现的站点专有判断（例如某站点特有的字段名）都应被视为分层错误。
- 域名发现留在适配器内，但必须复用档案的发布页体系产出候选基站，而不是另起一套硬编码列表；发布页里「随机前缀 + 域名池」这类形状属于站点专有细节，只影响适配器如何解析，不影响应用如何存储。
- 健康状态按出口计量（见 ADR-0006），档案级徽章是各出口的聚合。
