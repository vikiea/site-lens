# 站点档案同时具备直连出口与浏览出口

**Status**: accepted

## Context

站点档案（`SiteProfile`）已经是产品的第一等对象：它聚合发布页、候选落地页、绑定脚本与健康状态，「发布页镜像发现」是既有能力。要接入只提供接口的站点，最省成本的形状是让这份档案多一条出口，而不是新增一个平行对象——否则发布页发现、存活检查、粘 URL 侦察都要各写两遍。

## Decision

站点档案增加**出口**维度，出口只有两种：直连出口与浏览出口。同一份档案可以同时具备两者，它们并列、共用下游（媒体候选、媒体任务、下载、边下边播、导出、租约）。

直连出口由**站点适配器**实现（边界见 ADR-0004）；浏览出口沿用现有链路。下游只认媒体候选，不认出口。

直连出口的播放走远程直连、边播边缓存，下载是用户显式发起的独立动作（见 ADR-0005）；站点凭证由应用持有并跨进程注入（见 ADR-0007）；健康按出口计量（见 ADR-0006）。

镜像站是同一份档案的**浏览出口**：它在 WebView 里跑通自己的鉴权，应用只观察并接管媒体，不需要复刻它的协议。一个剧集在两条出口上各有线路，用户选的是一条线路，播放器拿的是一个候选。

## Rejected options

- **把应用改造成纯播放器、砍掉浏览链路**：下载、续传、边下边播、文件租约这些最贵的工程资产都在下游，与本决策无关；浏览出口在直连接口失效时是唯一的兜底手段。
- **新增平行概念 `DirectSite` 与档案并列**：发布页发现、存活检查、侦察要写两遍。唯一的反向论据是「平行新表零迁移成本」，但一次加列迁移的代价远低于长期维护两套发现体系。
- **把直连出口伪装成浏览出口**（伪造来源页喂给授权刷新）：直连出口没有页面可重放，刷新会永远落到「需回来源页」。

## Consequences

- 上游有两套语言（来源页 / 授权刷新 与 适配器 / 凭证刷新），下游共用一套。新增的媒体相关概念必须说明它属于哪一侧，否则会被塞进错误的层。
- 原生的本地文件路径（含边下边播）保持不动；远程路径按候选是否已有可播放本地文件分流。
- 首期验收顺序：服务接受远程 scheme（不带凭证）→ 凭证注入 → 缓存层 → 失败归因与刷新链 → 直连出口 UI → 批量下载与边下边播收窄。每一步单独跑一次设备验收，因为最重的一刀落在 `NativeMediaSessionService` 上。
