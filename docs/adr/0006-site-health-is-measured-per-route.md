# 站点健康按出口计量，档案徽章是聚合

**Status**: accepted

## Context

`ProfileHealth` 目前是每个档案一条记录，状态 `unknown / ok / failing`，由后台存活检查更新，注释明确写着「never feeds ranking or recommendations」。

一旦档案同时具备直连出口与浏览出口，这个模型就说不出真话：直连接口挂了但镜像站还活着，是这类站点的常态。档案级单一状态会让用户看到「站点可用」却点不动，或者反过来「站点故障」而无视还能用的那条出口。

## Decision

健康状态按**出口**计量：每条出口（以及出口内的每条发布页）各有自己的可用性记录，档案徽章由各出口聚合得出。

- 既有 `profile_pages.refreshed_at / error` 字段承担发布页级别的结果，不再只是「最后一次刷新时间」。
- 聚合规则对用户透明：任一出口可用即档案可用，全部不可用才报故障；失败的细节留给站点详情页。
- 健康仍是**尽力而为**，不参与排序与推荐。这一条不因出口拆分而改变。

## Rejected options

- **维持档案级单条健康**：无法表达「客户端接口挂了、镜像还能用」，而这恰恰是这类站点最常见、也最需要解释的故障形态。
- **只在直连出口上做健康检查**：浏览出口同样会失效（发布页被封、落地页改版），只检查一半等于把另一半的故障交给用户发现。

## Consequences

- 健康数据需要一次结构变化（每出口一条）。它可以与 ADR-0004 的通道字段同批落地，但审计时应当分开记录。
- 用户可见的故障文案必须能指出「哪条出口失败」，否则按出口计量在 UI 上等于没有发生。
- 站点详情页要能显示当前可用基站与出口状态；这是故障可见性的最低要求，不能被「运维界面降级到设置」一并降级。
